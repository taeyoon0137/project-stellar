# ADR-0005: 3계층 에이전트 도구 구조와 사용자 구독 CLI 연결형 내장 에이전트

## Status

Accepted (2026-11-14, 제품 소유자 결정). 제안 당시의 열린 질문은 2026-11-14 제품 소유자 결정으로 모두 정했고, 결정 내용은 아래 Decision에 반영했습니다.

## Context

- Stellar의 원본은 프로젝트 폴더와 Git 저장소의 파일이고, 문서 의미와 파일 포맷은 공통 Rust 코어가 소유합니다. 셸은 의미를 소유하지 않습니다(§8.1).
- Stellar 자체 AI 모델과 에이전트 런타임은 영구 비목표입니다(§4.3). 개정 전 기준(§31.1, §31.2)에서는 외부 CLI 에이전트가 터미널에서 실행되고 `stellar-mcp` 브리지로 실행 중 앱에 접속합니다.
- 요구사항은 세 가지입니다.
  1. 사용자가 이미 쓰는 AI 구독으로 열린 문서를 앱 안에서 바로 편집합니다. 에이전트는 캔버스 옆에 두고, 세션·입력·승인·미리보기를 제공합니다.
  2. 외부 에이전트와 스크립트도 같은 능력을 쓸 수 있어야 합니다.
  3. Stellar는 자체 모델과 자체 에이전트 런타임을 계속 갖지 않습니다.
- Headless CLI는 CI와 Git merge driver에서 앱 없이 동작해야 합니다(XXIV.1~XXIV.3).
- 2026-11-14 제품 소유자 결정은 다음과 같습니다.
  1. **구독 CLI 실행 조건**: 사용자가 설치하고 직접 로그인한, 수정하지 않은 공급자 공식 CLI를 각 CLI 공식 문서가 정한 비대화형 인터페이스로만 실행합니다. Stellar는 인증·자격 증명·사용량 중개에 참여하지 않습니다(§4.1).
  2. **출력 표시**: 채팅 보기와 원문 보기를 함께 제공하고, 기본은 채팅 보기입니다(§4.4).
  3. **headless 읽기 backend**: 앱 없이 동작하는 읽기 전용 MCP backend를 허용합니다(§3).
  4. **세션 종료**: 세션이 끊기거나, 비정상 종료되거나, 중지돼도 적용된 변경을 즉시 되돌리지 않습니다. 변경에 출처 표시를 남기고 사용자가 직접 되돌립니다(§4.2).
  5. **계획서 폐기 기록 없음**: 목적이 사라진 행은 폐기 표기 없이 삭제하고 이력은 Git으로 확인합니다.
  6. **커밋 형식**: `AGENTS.md` 기준으로 이미 맞췄습니다(계획서 개정 기록 "2026-11-14 — 커밋 규칙 정합").
  7. **명령 이름과 설치**: headless 명령은 `stellar`로 실행하고, `stellar`를 쓸 수 없는 경우에만 `stellar-cli`로 대체합니다(판정 조건은 §2). 앱 첫 실행 때 이 명령을 사용자 셸 PATH에 설치하는 화면을 제공하고, 사용자가 동의할 때만 설치합니다(macOS, §2, §7).
- 계획서의 기존 행 XIX.1.4, XIX.3.3, XIX.6.1, XIX.6.3, XIX.6.4, XIX.7.2는 이 결정과 의미가 충돌합니다. 모두 미착수 행이므로 2026-11-14 개정한 계획 변경 규칙에 따라 그 자리에서 고치고, 목적이 사라진 행은 삭제합니다.
- 이 ADR은 §4.3을 바꾸지 않습니다. §31의 경계를 명확히 하고 확장합니다.
- Windows 지원은 ADR-0006에 따라 보류하므로 이 ADR의 플랫폼 항목은 macOS만 다룹니다. L1·L2 library 경계는 플랫폼 중립으로 둡니다.

## Decision

### 1. 3계층 구조와 의존 방향

| 계층 | 구성 요소 | 역할 | 실행 중 앱 필요 여부 |
|---|---|---|---|
| L1 | `stellar` 명령(package `stellar-cli`), `stellar-ops` | AI와 무관한 headless 파일 도구. core crate로 프로젝트를 조회·검증·편집 | 필요 없음 |
| L2 | `stellar-mcp`, `stellar-agent-protocol` | L1 library의 능력을 MCP tool·resource로 노출하는 어댑터 | 읽기는 없어도 됨. 쓰기는 앱 필요 |
| L3 | 내장 에이전트 UI, `stellar-agent-host` | 사용자 구독 CLI를 호스팅하고 L2와 연결하는 사용자 화면 | 앱 자체 |

- 아래 계층은 위 계층을 알지 못합니다. 이 관계는 crate 의존 그래프 검사로 강제하며, 직접 의존뿐 아니라 전이 도달도 검사합니다.
- L1에는 AI, MCP, 모델, 에이전트 관련 명령과 의존이 없습니다.
- L2는 L1 library를 in-process로 호출합니다. 실행 중 앱과는 공용 protocol crate의 정의로만 통신합니다.
- L3는 L2를 별도 프로세스로 실행하며, L2의 구현에 의존하지 않습니다.
- `stellar` 명령은 실행 중 앱의 얇은 클라이언트가 아닙니다. 파일이 원본이고 CI와 merge driver가 앱 없이 돌아야 하므로, 실행 중 앱은 프로젝트 파일을 쓰는 여러 writer 중 하나입니다.

### 2. L1: `stellar` 명령

- **실행 이름**
  - 사용자가 부르는 명령은 `stellar`입니다. Cargo package 이름은 `stellar-cli`로 두고 실행 파일 이름(`[[bin]]`)만 `stellar`로 정합니다.
  - **대체 이름 규칙(결정 7 "`stellar`를 쓸 수 없으면 `stellar-cli`"에 대한 이 ADR의 해석)**: 사용자 셸 PATH에서 `stellar`라는 이름이 Stellar가 설치한 자기 링크가 아닌 다른 프로그램으로 먼저 해석되면(설치 위치에 이미 있거나, PATH 앞쪽에 있어 가려지는 경우) `stellar-cli`라는 이름으로 설치합니다. 다른 프로그램의 파일은 덮어쓰지 않습니다. `stellar-cli` 이름도 다른 프로그램이 쓰고 있으면 설치하지 않고 사용자에게 알립니다. 설치 화면은 실제로 설치한 이름을 보여 줍니다. 판정과 설치는 XXIV.5에서 구현합니다(§7).
  - XXIV.1.2의 JSON 결과 schema 식별자와 fixture는 바꾸지 않습니다.
  - 문서, 도움말, 종료 코드 설명은 `stellar <명령>`으로 표기합니다.
- **명령**
  - 기존 계획: `validate`, `semantic-diff`, `semantic-merge`, `migrate`
  - 추가: `inspect`, `query`, `apply`
    - `apply`는 파일이나 표준 입력으로 CommandTransaction JSON과 base revision을 받습니다.
    - `--dry-run`을 주면 semantic diff만 출력합니다.
- **출력**: 표준 출력에는 JSON 결과만, 표준 오류에는 진단만 씁니다.
- **쓰기**
  - 세대 전환 저장 직전에 교차 프로세스 저장 잠금을 잡고, 디스크 generation과 base generation을 비교합니다. 잠금은 프로젝트 폴더와 Git 밖의 OS 사용자 데이터에 둡니다.
  - 저장한 generation에는 writer 종류(앱 창, headless CLI)를 기록합니다.
  - 잠금을 쓰고 있으면 일시적 실패로 끝납니다.
- **merge driver 모드**: Git이 넘긴 임시 경로만 씁니다. 그래서 저장 잠금과 앱 공존 검사 대상이 아닙니다.
- **실행 중 앱과의 공존**
  - L1 쓰기는 앱이 같은 프로젝트를 열고 있어도 막지 않습니다. 시스템 Git이나 외부 편집기와 같은 외부 변경입니다(§22.5).
  - 앱은 writer 종류가 앱 창이 아닌 generation을 §22.2의 두 선택지 정책이 아니라 §22.5의 semantic reconciliation 경로로 처리합니다. 그래서 사용자가 선택하는 순간 CLI 변경이 덮어써지는 일이 없습니다.
  - 변경이 에이전트 lease와 겹치면 §4.2 종료 절차로 그 에이전트 세션을 끝냅니다(자동 rollback 없음). 적용된 에이전트 변경은 출처 표시를 유지한 로컬 변경으로 §22.5 reconciliation에 넣고, 의미 충돌은 Semantic Conflict 경로로 보냅니다.
  - L1 쓰기는 에이전트 출처 표시 대상이 아닙니다.
- **종료 코드**: sysexits 정의를 근거로 하며, 표는 XXIV.1.2가 소유합니다. 초안 대응은 다음과 같습니다.

| 코드 | 근거 | 의미 |
|---|---|---|
| 0 | 성공 | 성공 |
| 1 | 도메인 실패 | 검증 진단 있음, 미해결 semantic conflict, 거부된 command |
| 64 | EX_USAGE | 사용법 오류 |
| 65 | EX_DATAERR | 입력 schema 오류, base revision 불일치 |
| 66 | EX_NOINPUT | 프로젝트를 찾거나 열 수 없음 |
| 69 | EX_UNAVAILABLE | 요청한 동작에 필요한 Stellar 구성 요소를 쓸 수 없음 |
| 70 | EX_SOFTWARE | 내부 오류 |
| 73 | EX_CANTCREAT | 저장 실패 |
| 74 | EX_IOERR | 입출력 오류 |
| 75 | EX_TEMPFAIL | 저장 잠금 사용 중 |
| 76 | EX_PROTOCOL | 내부 protocol 버전 불일치 |
| 77 | EX_NOPERM | 권한 없음 |
| 78 | EX_CONFIG | 설정 오류 |

Git merge driver 모드에서는 0이 아닌 코드가 모두 충돌로 취급된다는 점을 문서화합니다. 128 이상은 신호용으로 남겨 둡니다.

### 3. L2: stellar-mcp

등록 기본값은 headless와 지정 프로젝트 절대 경로다(2026-11-18 결정). `stellar-mcp --connection-info --project <프로젝트 경로>`가 해당 경로를 포함한 stdio 등록 인자를 반환한다. 앱이 종료돼 있어도 저장된 프로젝트를 읽으며, 쓰기 권한과 신뢰 경계는 기존 headless backend 규칙을 따른다.

경로는 실제 절대 경로로 정규화하고 프로젝트 manifest(`stellar.yaml`)가 없으면 사용법 오류(64)로 끝낸다. 신뢰 확인은 headless 시작 때 한다. headless가 내는 tool은 읽기·검증·dry-run(propose)이다. 목록과 CLI 대응은 ADR-0085 결정 1·8이 정한다(예: `document.validate`, `document.propose_commands`, `document.propose_css_paste`, `document.source_span`, `git.status`). 쓰기 tool은 headless 목록에 없으므로, 앱 없이 같은 파일을 편집하는 쓰기는 `stellar` CLI(L1)의 `apply`·`css paste`·`git stage|unstage|commit`으로 한다. 이 CLI는 MCP dry-run과 같은 ops 함수를 쓴다(2026-11-23 개정, 이전 문장 "headless는 `semantic_diff`·`validate_document`만 제공"을 대체).

- **위치**
  - `tools/stellar-mcp` 실행 파일(XIX.1.1)은 진입점만 갖습니다.
  - 로직은 `crates/mcp-core`의 `stellar-mcp-core` library에 둡니다. 실행 파일 package `tools/stellar-mcp`는 실행 이름 `stellar-mcp`를 유지합니다.
  - 공용 정의는 `stellar-agent-protocol`에 둡니다.
- **backend**: 세션을 시작할 때 고정합니다.
  - **headless 읽기 backend**(2026-11-14 제품 소유자 결정으로 허용)
    - 실행 인자로 고정한 프로젝트 루트 하나만 다룹니다. tool 인자로 다른 프로젝트를 고를 수 없습니다.
    - 신뢰되지 않은 프로젝트에서는 모든 tool을 거부합니다.
    - 노출하는 tool은 L1의 읽기·검증·dry-run뿐이고, 쓰기 tool은 목록에 나타나지 않습니다.
    - 근거: 같은 사용자의 어느 프로세스든 이미 쓸 수 있는 L1 읽기 능력을 넘지 않습니다.
    - 앱이 없으므로 첫 연결 승인 대상이 아닙니다. 이 예외는 XIX.3.3이 정합니다.
  - **attached backend**
    - 검증된 실행 중 앱 endpoint에 붙습니다.
    - 모든 쓰기는 앱의 lease, 승인, DocumentThread 경로를 거칩니다.
    - 결합 단위는 프로젝트가 아니라 창 세션(WindowSessionId)입니다. 외부 클라이언트는 첫 연결 승인 화면에서 대상 창을 고르고, 앱이 시작한 세션은 시작한 창에 묶입니다.
    - backend 선택은 앱이 기록한 목록이 아니라 endpoint를 실시간으로 검증한 결과로 정합니다.
- **쓰기에 attached가 필요한 이유**
  - 앱 메모리의 미저장 상태 아래에서 파일을 바꾸면 저장 충돌이 생깁니다.
  - lease와 단일 Undo는 앱 DocumentThread에만 있습니다.
  - live 미리보기는 앱의 transient preview 경로에서만 가능합니다.
  - 승인은 네이티브 UI에서만 받습니다(§31.2).
- **카탈로그**
  - resource 목록(XIX.2.1)과 tool 목록(XIX.2.3)은 `stellar-agent-protocol`의 Rust 정의에서 생성합니다.
  - CommandTransaction 입력 schema는 xtask가 closed enum(VII.1.6)에서 생성한 산출물입니다. `stellar-agent-protocol`은 commands crate에 의존하지 않습니다.
  - tool 이름은 MCP 명세의 이름 규칙을 따르고, 읽기 계열과 파괴 계열에는 MCP annotation을 붙입니다.
  - Stellar 사용 안내는 MCP 명세에 따른 instructions로 제공합니다.
- **결과 종류**: tool 결과는 Stellar 승인·lease 모델(XIX.3, XIX.4, §31.3~§31.5)의 판정을 그대로 나타냅니다. 결과 범주는 XIX.3·XIX.4 판정을 그대로 나타내도록 XIX.9.5에서 정합니다.
  - 거부 사유는 Stellar 판정에서만 옵니다.
  - 응답이 없거나 세션이 끝나면 대기 중인 요청은 거부로 닫습니다(§4.2, §4.5 승인 요청 저장).
  - 오래 걸리는 호출과 클라이언트 취소는 MCP 명세를 따릅니다.
- **프로젝트 유래 문자열**: 프로젝트에서 온 문자열은 아키텍처 §37.1 신뢰 경계에 따라 데이터로만 다루며 지시로 해석되지 않게 합니다. 표현 방식은 XIX.9.6에서 정합니다.
- **변경 불가 경로**: MCP 경로에는 다음 상태를 쓰는 수단이 없습니다.
  - 프로젝트 신뢰 상태(XVI.7)
  - MCP 권한 상태(XIX.3)
  - 다른 세션의 lease(XIX.4)
  - 에이전트 모드
  - 앱 설정
  - terminal profile
  - 에이전트 변경 출처 표시와 되돌리기(§4.2)
  - 명령줄 설치 상태(§7)
- **외부 클라이언트 연결 정보**: MCP 클라이언트 등록에 필요한 정보를 제공하되 Stellar는 다른 도구의 설정을 바꾸지 않습니다. 제공 방식은 XIX.9.8에서 정합니다.

### 4. L3: 내장 에이전트

#### 4.1 제품 경계와 공급자 CLI 실행 조건(§31.1 명확화)

- Stellar는 다음을 두지 않습니다: 모델 제공자 API client, API key 입력·저장, 모델 라우팅, 과금·인증, 자체 agent loop.
- **실행 대상**: 사용자가 직접 설치하고 직접 로그인한 공급자 공식 CLI(모델 제공자가 배포하는 코딩 에이전트 CLI) 실행 파일 하나입니다. agent loop와 모델 호출은 그 CLI가 수행합니다.
  - Stellar는 공급자 CLI를 앱 번들에 넣거나 대신 설치·업데이트하지 않습니다. 실행 파일을 수정·패치·래핑하지 않습니다.
  - 설치와 업데이트는 각 CLI 공식 문서의 절차로 사용자가 직접 합니다.
- **실행 경로**: 각 CLI 공식 문서가 비대화형·프로그램 실행용으로 문서화한 인터페이스로만 실행합니다(§4.3).
  - 한 CLI가 문서화한 인터페이스를 여럿 제공하면, 공식 문서가 그 사용 형태에 인증 제한을 두지 않은 경로를 고릅니다. 인증 제한이 있는 경로는 제품 소유자가 검토해 승인한 뒤에만 씁니다.
- **공급자와의 관계**: 인증·자격 증명·모델 호출·사용량은 전적으로 CLI와 공급자 사이의 일이며 Stellar는 관여하지 않습니다(§31.1, §37.3, 2026-11-14 결정 1).
- **사용자 주도 실행**: 구독 CLI 세션은 사용자가 UI에서 명시적으로 시작할 때만 실행하고, 사용자 동작 없이 세션을 시작·재개하거나 요청을 다시 보내지 않습니다.
  - CLI가 보고한 사용 한도·인증 오류는 그대로 표시하고 세션을 멈춥니다.
  - 근거는 각 공급자 사용 정책과 Stellar의 사용자 주도 원칙(세션은 시작한 창에 묶이고 앱을 다시 시작하면 복원하지 않음, §4.2)입니다.
- **연결 상태**: CLI 사용 가능 여부의 판정은 XXIX.2.5 구현 작업에서 각 CLI 공식 문서를 근거로 정하고, CLI가 보고한 정보의 취급은 XVI.8 개인정보 규칙을 따릅니다.
- **약관 검토와 활성 목록**
  - launch profile마다 공급자 약관·공식 문서의 검토 일자와 검토 결과를 기록합니다. 공급자 문서와 약관은 자주 바뀌므로 검토 일자는 정기적으로 갱신합니다.
  - Stellar의 실행 조건은 2026-11-14 확인한 각 공급자 공식 약관·사용 정책의 범위 안에 머물도록 설계했습니다. 실제로 그 범위 안에 있는지의 최종 확인은 Consequences의 릴리스 위험 항목으로 남기며, Stellar를 추후 오픈소스로 공개할 예정이라는 점을 그 판단의 입력으로 둡니다.
  - 각 공급자 공식 약관·사용 정책이 2026-11-14 결정 1의 실행 방식(사용자가 직접 로그인한 공식 CLI를 Stellar가 비대화형으로 실행)을 명확히 허용하지 않거나 검토가 끝나지 않은 CLI는 profile 활성 목록에 넣지 않습니다(각 공급자 공식 약관).
  - 활성 목록에 없는 CLI는 사용자가 내장 터미널에서 일반 terminal profile 명령으로 직접 실행할 수 있습니다(XVIII.5.1).
  - 배포 주체의 상용 약관 동의 여부는 설계 결정이 아니라 릴리스 위험으로 다룹니다(Consequences).
- **약관 고지**: 각 CLI를 내장 에이전트로 처음 쓰기 전과 profile의 약관 검토 결과가 바뀐 뒤에 고지 화면을 보여 주고 사용자의 명시적 확인을 받습니다. 확인 기록은 프로젝트 폴더와 Git 밖의 OS 사용자 데이터에 둡니다. 고지 내용은 다음과 같습니다.
  - 사용자의 컴퓨터에 설치된 해당 CLI가 사용자 본인 계정으로 실행됩니다.
  - 해당 공급자의 약관, 사용 정책, 요금제 한도, 데이터 처리 방침이 적용됩니다.
  - Stellar는 인증·자격 증명·사용량에 관여하지 않습니다.
  - 에이전트가 Stellar tool로 읽은 프로젝트 데이터는 CLI를 거쳐 그 공급자에게 전송됩니다.
  - Stellar는 그 공급자와 제휴 관계가 없습니다.
- **상표 표시**: 공급자 CLI 이름은 사용자가 어떤 CLI를 실행하는지 알리는 일반 텍스트로만 씁니다. Stellar 기능 이름, 메뉴 이름, 아이콘에 공급자 이름이나 로고를 넣지 않고, 공급자가 Stellar를 만들었거나 보증·제휴한 것처럼 보이는 표현을 쓰지 않습니다.
- 사용자 문장은 그대로 CLI에 전달합니다. 시스템 프롬프트 템플릿은 저장하지도 편집하지도 않습니다.
- 모델 이름은 CLI가 보고한 값을 표시합니다. 세션 중에 모델이 자동으로 바뀌지 않게 합니다.

#### 4.2 세션 수명, 종료와 사용자 되돌리기

- **lease 소유**
  - 앱이 시작한 세션에서는 앱 쪽 AgentSession이 lease와 권한을 소유합니다. 그 세션에 결합된 bridge(§5)가 다시 연결되면 같은 세션에 다시 묶이며, 재연결 유예를 둡니다.
  - 외부 클라이언트 세션은 bridge 연결이 끝나면 종료됩니다.
- **세션 종료 조건**: 사용자 중지, bridge 연결 종료(외부 클라이언트), CLI 프로세스 종료, 재연결 유예 초과, 비정상 종료, 신뢰 철회, lease와 겹치는 외부 변경, 사용자의 lease 해제.
- **종료 절차**: 자동 rollback을 하지 않습니다.
  1. 적용 중인 CommandTransaction은 VII.1.6 원자성에 따라 전부 적용되거나 전부 미적용으로 끝냅니다.
  2. 이미 적용된 batch는 그대로 두고, origin이 에이전트(AgentSessionId)인 "중단됨" history entry 하나로 확정합니다.
  3. lease를 즉시 해제하고, 세션 권한과 세션 한정 승인을 폐기합니다.
  4. 사용자 응답을 기다리는 요청은 거부로 닫고, 적용 전 제안은 폐기하며, 열린 승인 화면을 닫습니다.
  5. 앱이 시작한 세션은 §4.3 불변식에 따라 실행 흔적을 남기지 않도록 정리합니다.
  6. 진단에는 session id, duration, error code만 남기고 내용은 남기지 않습니다.
- **정상 완료**(CompleteAgentEdit): 승인된 batch 전체를 Undo entry 하나로 확정하고 lease를 해제합니다.
- **출처 표시(provenance)**
  - 완료된 세션과 중단된 세션 모두, 적용된 batch(CommandTransaction 하나)마다 출처를 기록합니다: AgentSessionId, CLI가 보고한 세션 표시 이름, batch 순번, history sequence, Stellar 코어가 계산한 변경 노드·속성(VII.1.4 결과), StableId+PropertyPath별 적용 직후 값 지문, batch별 inverse transaction.
  - 표시 위치: 레이어 패널 노드 행, 인스펙터의 속성 단위 표시, 사용자가 켜고 끌 수 있는 캔버스 윤곽 overlay, 에이전트 패널의 세션별 변경 목록, 세션 목록의 검토 대기 개수. 캔버스 overlay는 렌더 프리뷰와 내보내기 산출물에 넣지 않습니다. 세션은 색에만 의존하지 않는 기호와 접근성 레이블로 구분합니다.
  - 변경 목록은 변경 단위마다 시각, Stellar semantic diff 요약, 상태(검토 대기 / 확인됨 / 이후 변경됨 / 실행 취소됨 / 되돌림)를 보여 주고 대상 노드로 이동할 수 있게 합니다.
  - 표시는 출처 정보이지 문서 상태가 아닙니다. 사용자가 변경 단위나 세션 단위로 "유지"를 고르면 표시만 지우고 변경은 남깁니다. 이 동작은 문서 bytes, Git 변경, history entry를 만들지 않습니다.
  - 표시가 있는 속성을 사용자, 다른 세션, 외부 변경이 다시 바꾸면 그 속성은 "이후 변경됨"이 됩니다. 창 Undo로 에이전트 entry를 취소하면 "실행 취소됨", Redo하면 원래 상태로 돌아갑니다.
  - headless `stellar` 쓰기와 CLI 에이전트의 직접 파일 편집(§31.6)은 출처 표시 대상이 아닙니다. 둘 다 일반 외부 변경입니다.
- **사용자 되돌리기**
  - 되돌리기는 사용자가 직접 실행합니다. 범위는 변경(승인 batch) 하나 또는 세션 전체입니다.
  - 되돌리기는 history 포인터 이동이 아니라 새 User origin CommandTransaction이며 DocumentThread에서 적용합니다. 창 history에 "에이전트 변경 되돌리기" entry 하나로 기록되고 일반 Undo/Redo 대상입니다.
  - 세션 전체 되돌리기는 남은 변경 단위를 역순으로 합친 한 트랜잭션이며, 전부 성공하거나 전부 미적용입니다(VII.1.6).
  - 전제조건은 문서 전체 revision 일치가 아니라 StableId+PropertyPath별로 현재 값이 에이전트 적용 직후 값과 같은지입니다. 다르면 충돌입니다. 충돌의 예: 이후 변경된 속성, 에이전트가 만든 노드 아래에 사용자가 추가한 자식이나 참조, 외부 inbound ref, 이미 삭제된 노드.
  - 충돌 항목은 자동으로 덮어쓰지 않습니다. 미리보기에서 항목별로 "현재 유지 / 에이전트 이전 값 복원"을 고르게 하고, 사용자 콘텐츠가 함께 사라지는 구조 충돌의 기본값은 "현재 유지"입니다.
  - 되돌리기 전에 네이티브 chrome(패널, sheet, dialog)에 Stellar 코어가 만든 semantic diff, validation 결과, 렌더 프리뷰를 보여 주며, 승인 전에는 문서 상태가 바뀌지 않습니다(XIX.5.3과 같은 경로). 다른 활성 lease 안에 있는 항목은 XIX.4.3에 따라 차단하고 이유를 표시합니다.
  - 사용자가 중지와 세션 되돌리기를 함께 고르면 종료 절차를 마친 뒤 세션 단위 되돌리기 미리보기를 엽니다. 별도 rollback 경로는 두지 않습니다.
  - 되돌리기 결과는 일반 편집과 같은 autosave 경로로 저장합니다.
  - 표시와 되돌리기는 세션이 묶인 창에서만 제공합니다. 같은 프로젝트의 다른 창은 저장된 generation을 일반 경로로 받으며 표시를 보여 주지 않습니다.
- **저장 범위**: 출처 표시와 되돌리기 정보는 세션이 묶인 창(WindowSessionId)의 메모리에만 둡니다. 프로젝트 파일, Git, generation metadata, 복구 snapshot, 진단, 텔레메트리에는 넣지 않습니다. 창을 닫으면 WindowHistory와 함께 폐기합니다(VII.5.4). 변경 자체는 남고 Git semantic status(§26)로 확인할 수 있습니다.
- **에이전트 경로 차단**: MCP tool, `stellar-mcp`, `stellar` 명령 어디에도 출처 표시를 지우거나 바꾸는 수단과 되돌리기 수단을 두지 않습니다(§3 변경 불가 경로).
- 세션은 시작한 창에 묶이고, 앱을 다시 시작하면 복원하지 않습니다.
- 이 규칙은 XIX.1.4, XIX.6.1\~XIX.6.4, XIX.6.7\~XIX.6.10, XIX.7.2, XXIX.2.8이 구현합니다.

#### 4.3 구독 CLI 실행 요구사항

- **불변식**: 근거는 Stellar의 MCP·승인·lease 모델(§31.2~§31.6)입니다.
  1. 문서 변경은 lease·승인·DocumentThread를 거치는 Stellar MCP tool로만 일어납니다(§31.3~§31.6). 승인은 Stellar 네이티브 UI에서만 받습니다(§31.2).
  2. 세션은 프로젝트 working tree와 사용자의 CLI·도구 설정에 흔적을 남기지 않습니다(§31.6, §3 다른 도구 설정 무변경 원칙).
- **launch profile**: CLI 종류와 지원 버전 범위마다 하나씩 Stellar가 소유한 fixture로 관리합니다. 각 profile은 각 CLI 공식 문서를 근거로 한 실행 설정, 출력 해석 규칙(§4.4 decoder profile), 공급자 약관·공식 문서 검토 일자와 결과를 담습니다.
- **profile별 보고서**: 두 불변식을 어떤 공식 설정으로 지키는지와 그 밖의 실행 세부는 각 CLI 공식 문서와 Apple 공식 문서를 근거로 profile별 보고서에 기록합니다.
- **profile 검증**: 자동 테스트는 네트워크와 실제 계정 없이 결정적으로 실행합니다(§38 테스트 층). 새 profile은 릴리스 전 수동 검증을 거쳐 추가하고, 결과는 해당 WBS 작업 보고서에 기록합니다.
- **실행 대상 확인**: 사용자가 확인한, 수정하지 않은 공식 CLI만 실행합니다(2026-11-14 결정 1). 지원 범위 밖 CLI 버전은 실행하지 않고, 약관 검토상 활성 목록에 없는 CLI도 실행하지 않습니다. 확인할 수 없으면 실행하지 않습니다(fail closed). 실행 파일 신원 확인 방법은 구현 작업에서 Apple 공식 문서와 각 CLI 공식 문서를 근거로 정합니다.

#### 4.4 출력 표시

- **두 보기**: 내장 에이전트 세션마다 채팅 보기와 원문 보기를 함께 제공합니다(2026-11-14 결정).
  - 새 세션과 앱 재실행 후의 기본값은 채팅 보기입니다.
  - 보기를 바꿔도 표시 상태만 바뀌고 CLI 프로세스, 권한, lease, 승인 요청에는 영향이 없습니다.
  - 보기 상태는 창 세션 메모리에만 두고 프로젝트 파일, Git, 복구 snapshot에 저장하지 않습니다.
- **채팅 보기 모델**: `stellar-agent-host`의 closed enum `AgentChatItem`으로 정의합니다. 구체 variant는 XXIX.2.10에서 정하며, 2026-11-14 결정(채팅 보기 기본)과 Stellar의 승인·출처 모델(§31.3~§31.5)이 요구하는 범위를 넘지 않습니다.
  - 채팅 보기는 문서 상태나 승인 결과의 근거가 아니며, 문서 효과 표시는 Stellar 승인·출처 기록과 일치해야 합니다(§31.3~§31.5).
- **표시 안전**: 에이전트 텍스트와 프로젝트 유래 문자열은 신뢰하지 않는 입력으로 다룹니다(§37.1과 같은 원칙). 표시 과정에서 네트워크 요청, 스크립트 실행, WebView 생성이 일어나지 않습니다. 서식 범위는 XXIX.4.3 구현 작업에서 정합니다.
- **원문 보기**: CLI 출력을 가공 없이 읽기 전용으로 보여 주고, 디코더의 성공·실패와 관계없이 보존합니다.
  - 세션은 PTY가 아닌 파이프로 비대화형 실행하므로 제어 문자는 해석하지 않습니다. terminal emulation은 하지 않습니다.
  - 원문 버퍼는 세션마다 메모리 상한을 둡니다. 상한 값과 초과 처리 방식은 구현 작업에서 실측으로 정합니다.
- **디코더 위치**: 공급자 출력 디코드는 표시 전용이며 `stellar-agent-host` 계층 안에 격리합니다(2026-11-14 결정). 다른 crate, 셸 코드, FFI에는 공급자 출력을 해석하는 코드가 없습니다. 모듈 구성과 입출력은 XXIX.2.11 구현 보고서에서 정합니다.
- **decoder profile**: launch profile(§4.3)마다 버전이 붙은 decoder profile을 하나씩 둡니다. 각 CLI 공식 문서가 정의한 비대화형 구조화 출력 형식만 해석합니다.
- **fail closed**: 2026-11-14 결정에 따라 디코드는 실패하면 닫힙니다. 디코드 실패는 문서 상태와 권한을 바꾸지 않고 적용된 변경을 되돌리지 않습니다(§4.2). 판정 기준과 실패 뒤 처리는 각 CLI 공식 문서를 근거로 profile별 구현 보고서에 기록합니다.
- **권한 주체 아님**: 문서 읽기와 편집의 허용 여부는 앱의 MCP 권한, 승인, lease 모델(XIX.3, XIX.4)만 결정합니다. 디코드 실패 판정은 권한을 넓히거나 좁히는 수단이 아닙니다.
- **문서 변경 경로 금지**: `AgentChatItem`과 디코더 내부 타입은 CommandTransaction이나 document, commands, history, storage, ops 타입을 담지 않고, 그 타입이나 승인 응답으로 변환하는 함수도 갖지 않습니다. 에이전트 텍스트를 해석해 Command를 만드는 기능도 두지 않습니다. 모든 편집은 CLI가 호출한 stellar-mcp tool에서 앱 승인과 DocumentThread를 거치는 경로로만 일어납니다. 이 경계는 타입 inventory와 §8 전이 도달 금지 규칙으로 검사합니다.
- **테스트**: 디코더 테스트는 원문 입력과 기대 결과(golden)로 네트워크, 실제 계정, 모델 호출 없이 결정적으로 실행합니다(§38). fixture에는 XVI.8 금지 정보를 넣지 않습니다. 같은 원문은 항상 같은 결과로 디코드되어야 합니다.
- **기록**: 원문과 채팅 기록은 세션 메모리에만 두며 진단, 텔레메트리, 복구 snapshot, 프로젝트, Git에 넣지 않습니다.
- **터미널 경로와의 분리**: 내장 터미널에서 CLI를 대화형으로 실행하는 경로(XVIII.5.1)는 내장 에이전트 세션과 별개로 유지하며, 그 경로에는 공급자별 출력 디코더를 적용하지 않습니다.

#### 4.5 패널과 승인의 정책 경계

화면 배치와 조작 세부는 XXIX.4 구현 작업이 플랫폼 HIG를 근거로 정합니다.
- **패널**: 에이전트 UI는 캔버스 렌더 경로 밖의 네이티브 chrome에 두고 캔버스 위에 겹쳐 그리지 않습니다(§6.2~§6.4 인터랙션 성능 계약). 패널은 창마다 하나이고, 세션은 시작한 창에 묶입니다(§4.2). 패널을 숨겨도 세션과 승인 대기는 유지됩니다.
- **승인 화면 위치**: 네이티브 chrome(패널, 창 sheet 또는 dialog)에만 둡니다. 캔버스와 플러그인 WebView 안에는 그리지 않습니다.
- **승인 근거**: Stellar 코어가 만든 semantic diff, validation 결과, 렌더 프리뷰를 승인 근거로 보여 줍니다(XIX.5.3). 화면 구성은 XXIX.4 구현 보고서에서 정합니다.
- **민감 확인**: Terminal, FileDelete, GitCommit, GitPush 확인은 플랫폼 HIG의 파괴적 동작 확인 패턴을 따르고, 보조 기술로 확정할 수 있어야 합니다.
- **승인 요청 저장**: 승인 요청은 ProjectIdentity 단위로 코어에 보관하고, 첫 응답 하나만 유효합니다. 응답이 없거나, 창이 닫히거나, 세션이 끝나면 거부로 처리합니다.
- **모드**: 세션에 줄 수 있는 Stellar 권한(XIX.3.1의 Read·Propose·Apply)의 조합을 고르는 사용자 설정입니다. 모드는 권한을 부여하지 않고 상한으로만 작동하며, 승인은 XIX.3 모델이 따로 받습니다. 모드는 §3 변경 불가 경로에 속하므로 프로젝트 파일이나 에이전트 경로로 바꿀 수 없고, 사용자 UI에서만 바꿉니다(Security). 범위 승인은 모든 모드에서 필요합니다.

| 모드 | 권한 상한 |
|---|---|
| 읽기 전용 | Read |
| 검토 후 적용(기본) | Read, Propose (batch마다 승인) |
| 승인 범위 내 바로 적용 | Read, Propose, Apply |

- **내장 세션 카탈로그**: Terminal, FileDelete 계열 tool을 노출하지 않습니다. GitCommit과 GitPush는 개별 확인으로만 허용합니다.
- **세션 시작 조건**: 신뢰된 프로젝트에서만 시작합니다. 사용자가 대상 프로젝트, 실행할 CLI, 모드를 확인하고 시작하며, 이 확인을 첫 연결 승인으로 기록합니다(§31.3). 신뢰를 철회하면 즉시 세션을 중지하고 §4.2 종료 절차를 따릅니다.
- **중지와 lease 해제**: 사용자는 세션을 중지하거나, 중지하고 그 세션의 변경을 되돌리거나, 에이전트 lease를 해제할 수 있습니다(§31.5). 모두 §4.2 종료 절차를 따르며 적용된 변경을 지우지 않고, 되돌리기는 §4.2 사용자 되돌리기 미리보기를 거칩니다. 이 동작의 메뉴 항목, 이름, 배치는 XXIX.4 구현 작업에서 HIG를 근거로 정합니다.
- **창과 앱 종료**: 활성 lease, 실행 중인 세션, 검토 대기 출처 표시가 있으면 창 닫기와 앱 종료 전에 사용자에게 확인합니다. 출처 표시는 창과 함께 사라지고 변경은 남는다는 점을 알리며(§4.2 저장 범위), 사용자가 되돌리기를 고르면 §4.2 미리보기를 거칩니다.
- **접근성**: 에이전트 UI는 플랫폼 네이티브 접근성 API와 키보드 조작을 지원합니다(§18 Stellar 애플리케이션 자체 UI).

### 5. 로컬 제어 채널과 신원 확인

- 네트워크 포트는 열지 않습니다(§31.2).
- IPC 양쪽은 데이터 교환 전에 상대를 인증합니다(아키텍처 §37 신뢰 경계).
- 앱이 시작한 bridge는 그 세션에만 결합되고, 세션이 끝나면 결합 수단은 무효가 됩니다(§31.3). 결합은 권한이 아니며 XIX.3 승인을 대체하지 않습니다.
- 인증 기준, 결합 수단, endpoint 위치와 사용할 OS API는 WBS 구현 작업에서 Apple 공식 문서와 각 CLI 공식 문서를 근거로 정합니다.

### 6. 스레드와 성능

- 앱에 "Agent Host·IPC I/O 스레드"를 둡니다. 이 스레드는 문서를 쓰지 않습니다.
- 검증된 Command는 일반 DocumentThread queue에 사용자 입력보다 낮은 priority로 들어갑니다. queue가 넘치면 tool 결과로 busy를 돌려줍니다.
- lease 대상 계산과 batch 적용은 UI·문서 스레드 단일 점유 상한(§6.3)을 넘지 않게 나눠 처리합니다.
- 상대 인증처럼 느릴 수 있는 호출은 UI·문서 스레드 밖에서 합니다.
- 승인 이벤트와 채팅 item 변경분은 기존 FFI pull 방식 event 경로(II.4.5)로 셸에 전달합니다.
- 디코드, 원문 버퍼링, 표시용 텍스트 준비는 Agent Host·IPC I/O 스레드나 worker에서 합니다. UI 스레드는 준비된 변경분만 반영하고 단일 점유 상한(§6.3)을 지킵니다.
- UI가 느려도 CLI 출력 수신은 멈추지 않습니다. 메모리는 원문 버퍼 상한으로 제한합니다. 에이전트가 최대 속도로 출력하는 동안에도 캔버스 인터랙션 지연 계약(§6.2~§6.4)을 지키는지 성능 게이트로 검사합니다.

### 7. 배포와 명령줄 설치

- **macOS 번들 구성**
  - 앱 번들에 `stellar`와 `stellar-mcp`를 helper로 넣습니다.
  - `stellar`는 L1(Phase XXIV)이 준비된 빌드부터 넣으며 L2·L3 진행을 기다리지 않습니다. `stellar-mcp`는 L2(Phase XIX)가 준비된 빌드부터 넣고, 내장 에이전트는 Phase XXIX 작업으로만 노출합니다.
  - helper와 앱은 Apple 공식 코드 서명·공증 문서에 따라 서명하고 공증합니다. helper에는 앱 entitlement를 주지 않습니다. 번들 안 배치와 구체 서명 옵션은 XXIV.5.1 구현 보고서에서 정합니다.
  - 기존 릴리스 서명 스크립트의 "중첩 서명 대상 없음" 전제를 바꿔야 합니다.
- **Windows**: ADR-0006에 따라 보류합니다.
- **headless·CI 머신**: `stellar` 단독 서명·공증 배포물을 제공하며 `stellar-mcp`는 넣지 않습니다.
- **노출 시점**: AI와 무관한 L1 `stellar` 명령과 명령줄 설치 화면은 준비되는 대로 앱에 포함할 수 있습니다. L2(`stellar-mcp`)와 L3(내장 에이전트)는 해당 Phase가 끝난 뒤 노출합니다.
- **명령줄 설치(macOS, 2026-11-14 제품 소유자 결정)**: 앱 UI에서 제공합니다.
  - **첫 실행 제안**: `stellar` helper를 포함한 빌드를 처음 실행할 때 명령을 사용자 셸 PATH에 설치하는 화면을 제공합니다.
  - **동의**: 사용자가 명시적으로 동의하기 전에는 어떤 파일도 만들거나 바꾸지 않습니다.
  - **설치 이름**: 기본은 `stellar`입니다. PATH에서 `stellar`가 다른 프로그램으로 해석되면 덮어쓰지 않고 `stellar-cli`로 설치하고, 그 이름도 쓰이고 있으면 설치하지 않고 알립니다(§2 대체 이름 규칙).
  - **설치 조건**: 설치 위치, 제거 방법과 안전 조건은 §37 보안 경계(최소 권한)와 Apple·각 셸 공식 문서를 근거로 XXIV.5 구현 작업에서 정하고 보고서에 기록합니다.
  - **기록**: 설치 상태는 앱 사용자 설정(OS 사용자 데이터)에만 두고 프로젝트, Git, 텔레메트리에는 남기지 않습니다. MCP와 에이전트 경로에는 설치 상태를 바꾸는 수단이 없습니다(§3 변경 불가 경로).
- **비밀 관리**: 서명 인증서, 팀 식별자, 공증 자격 증명은 저장소에 두지 않습니다.

### 8. crate 배치

| crate | 위치 | 허용 직접 의존 | 전이적으로도 도달 금지 |
|---|---|---|---|
| `stellar-ops` | `crates/ops` | project, document, commands, history, storage, semantic-diff, semantic-merge, diagnostics, codegen, accessibility, target-profile(ADR-0049의 `export-web` 연결), git-porcelain(ADR-0080의 `stellar git` 연결) | local-ipc, agent-protocol, mcp-core, agent-host, ffi |
| `stellar-cli`(package, 실행 이름 `stellar`) | XXIV.1.1이 정한 위치 | ops, diagnostics | local-ipc, agent-protocol, mcp-core, agent-host |
| `stellar-local-ipc` | `crates/local-ipc` | core-types | document, commands, ops |
| `stellar-agent-protocol` | `crates/agent-protocol` | core-types | commands, document, ops, agent-host |
| `stellar-mcp-core`(library) | `crates/mcp-core` | ops, agent-protocol, local-ipc, diagnostics | agent-host, runtime, ffi |
| `stellar-agent-host` | `crates/agent-host` | core-types, agent-protocol, local-ipc, diagnostics | document, commands, history, storage, ops |
| `stellar-runtime` | `crates/runtime` | ADR-0013 §2 목록에 더해 agent-host, agent-protocol, ops, 에이전트 편집 구현 crate | mcp-core |
| `stellar-ffi` | `crates/ffi` | core-types, runtime(ADR-0013 §2) | (타입 변환 금지 inventory로 보완) |

- attached tool 호출은 `stellar-agent-protocol`이 정의한 host trait로 처리하고, `stellar-runtime`이 구현합니다.
- FFI 경계는 ADR-0013을 따릅니다. `stellar-ffi`는 core-types와 runtime에만 의존하고, 에이전트 기능은 agent-host와 ops를 품은 `stellar-runtime`을 거쳐 도달합니다. runtime 허용 의존의 추가는 XXIX.3.1에서 적용합니다.
- 실행 파일 package `stellar-mcp`(`tools/stellar-mcp`)는 진입점만 갖고 `stellar-mcp-core`에 의존합니다(XIX.9.1).
- XIX.4~XIX.6의 구현 crate는 그 작업에서 정하되, `stellar-agent-host`에서 그 crate로 도달하지 않게 합니다.
- 공급자 출력 디코드는 `stellar-agent-host` 안에만 둡니다(§4.4).
- `render_preview`는 attached 전용입니다.

### 9. 구현 세부 결정 원칙

- ADR에는 경계, 불변식, 결정만 둡니다.
- 수치, OS API, UI 세부 같은 구현 세부는 해당 WBS 구현 작업에서 Stellar 실측과 OS·CLI 공식 문서를 근거로 정하고 작업 보고서에 기록합니다.

## Alternatives

- **API key를 받아 Stellar가 직접 tool loop를 도는 방식**: 자체 런타임과 비밀 저장소가 필요해 §4.3과 §37.3에 위배됩니다. 채택하지 않습니다.
- **Stellar가 모델 제공자 인증 흐름에 직접 참여하는 방식**: §31.1의 "모델 선택·과금·인증 없음"과 §37.3에 위배됩니다. 채택하지 않습니다.
- **CLI를 내장 터미널에서만 대화형으로 실행하는 방식**: 공급자 출력 처리가 필요 없습니다. 하지만 세션 목록, 단계 표시, 작업 대상 지정, 승인 연계를 제공할 수 없습니다. 보조 경로로는 계속 지원합니다.
- **원문 보기만 제공하는 방식**: 단계·승인·미리보기·적용 변경을 대화 흐름 안에서 보여 줄 수 없습니다. 원문 보기는 디코더 실패에도 정보를 잃지 않는 보조 보기로 유지하고, 기본은 채팅 보기로 합니다(2026-11-14 결정).
- **세션이 끊기면 즉시 자동 rollback하는 방식**: 사용자가 검토하려던 작업이 연결 문제만으로 사라집니다. 적용분을 유지하고 출처를 표시해 사용자가 직접 되돌리게 합니다(2026-11-14 결정).
- **되돌리기를 history 포인터 이동이나 Undo 기록 없는 rollback으로 두는 방식**: 에이전트 변경과 lease 밖 사용자 편집이 섞여 개별 batch를 되돌릴 수 없고, 되돌리기 자체를 Undo할 수 없습니다. 일반 사용자 Command로 둡니다.
- **`stellar-cli`를 기본 명령 이름으로 쓰는 방식**: 사용자가 부르는 이름이 길어집니다. 기본 실행 이름은 `stellar`, package 이름은 `stellar-cli`로 분리하고, `stellar-cli`는 §2 대체 이름 규칙에 해당할 때의 설치 이름으로만 씁니다(2026-11-14 결정).
- **관리자 권한이 필요한 시스템 위치에 설치하는 방식**: §37 보안 경계의 최소 권한 원칙에 맞지 않습니다. 기본으로 채택하지 않습니다.
- **`stellar` 명령을 실행 중 앱의 얇은 클라이언트로 만드는 방식**: 파일이 원본이고 CI와 merge driver가 앱 없이 돌아야 한다는 조건에 맞지 않습니다. 채택하지 않습니다.
- **headless backend에서 쓰기를 허용하는 방식**: 앱의 승인·lease를 우회하고, 쓰기 허용 스위치가 에이전트가 고칠 수 있는 파일에 남게 됩니다. 채택하지 않습니다.
- **앱이 프로젝트를 열고 있으면 `stellar` 쓰기를 거부하는 방식**: 외부 변경 원칙(§22.5)과 일관성이 없고, 앱이 열린 동안의 Git merge를 막습니다. 채택하지 않습니다.
- **충돌 행을 폐기 표기로 남기고 대체 ID를 연결하는 방식**: 계획서와 ledger에 폐기 기록 체계가 필요합니다. 이력은 Git에 남으므로 미착수 행은 그 자리에서 고치고 목적이 사라진 행은 삭제합니다(2026-11-14 결정).

## Consequences

- **그 자리에서 고친 행**: XIX.1.4(연결 종료 event), XIX.3.3(headless 읽기 예외), XIX.6.1(batch별 inverse 보존), XIX.6.3(중지는 rollback 없음), XIX.6.4(종료 절차), XIX.7.2(겹치는 외부 변경), Phase XIX 완료 조건.
- **책임 위치**: 터미널 경로의 공급자 parser 금지 검사는 XXIX.6.6이 담당하고, 되돌리기 결과는 일반 autosave 경로(XIX.6.8)로 저장합니다.
- **유지되는 행**: XIX.1.1, XIX.1.2, XIX.1.3, XIX.1.5, XXIV.1.1, XXIV.1.2, XVI.9.3, XVI.11.8은 그대로 둡니다. 실행 이름 `stellar`는 신규 XXIV.4.1에서 적용합니다.
- **신규 WBS**: XIX.1.6\~XIX.1.9, XIX.6.7\~XIX.6.10, XIX.9, XXIV.4, XXIV.5, Phase XXIX.
- **crate graph 검사기 확장**: 전이 도달 금지 규칙과 target·build·dev 의존 파싱을 추가합니다.
- **새 외부 의존성**: JSON 직렬화, JSON-RPC 프레이밍, IPC 상대 인증용 OS binding, 필요하면 표시 서식 해석은 승인 목록에 등록해야 합니다.
- **Phase VII 요구 추가**: 속성 단위 되돌리기 전제조건과 구조 충돌 판정이 필요합니다. 진행 중인 VII 행은 바꾸지 않고 XIX.6.8이 VII 산출물 위에서 구현합니다.
- **유지보수 비용**: CLI 갱신은 launch profile 갱신 작업을 요구하고, profile의 약관 검토 일자도 정기적으로 갱신해야 합니다.
- **부정**: 출처 표시는 창을 닫거나, 앱을 다시 시작하거나, 비정상 종료 복구를 거치면 사라집니다. 그 뒤에는 Git semantic status로만 확인할 수 있습니다.
- **부정**: 공급자 조건에 따라 활성 목록에 넣을 수 있는 CLI가 없거나 적을 수 있습니다. 그 경우에도 내장 터미널 경로는 남습니다.
- **릴리스 위험(제품 소유자 법무 확인 필요)**: 2026-11-14 확인한 공개 공급자 문서 중에는 자사 CLI를 제품 안에서 실행하는 배포 주체에게 그 공급자의 상용 약관 동의를 요구하는 곳이 있고, 프로그램 실행용 인증을 상용·호스팅 서비스에 허용하지 않는다고 적은 곳이 있습니다. Stellar가 이 조건에 해당하는지는 설계 결정이 아니라 릴리스 전에 제품 소유자가 법무 검토로 확인할 항목입니다. Stellar를 추후 오픈소스로 공개할 예정이라는 점을 이 판단의 입력으로 포함합니다. 확인 전에는 해당 CLI를 활성 목록에 넣지 않습니다(§4.1).

## Compatibility

- 문서 의미와 파일 포맷은 바뀌지 않습니다.
- writer 종류 metadata는 storage의 generation metadata에 추가되며, 기존 generation은 앱 창 writer로 해석합니다.
- 잠금, 세션, 권한, transcript, 에이전트 변경 출처 표시는 프로젝트 파일과 Git에 저장하지 않습니다.
- 실행 이름 `stellar`로 바꿔도 XXIV.1.2의 JSON 결과 schema 식별자는 바뀌지 않습니다.
- 명령줄 설치 상태와 약관 고지 확인 기록은 OS 사용자 데이터에만 있습니다.

## Performance

- CLI 프로세스와 IPC는 핵심 입력·편집·렌더링 경로 밖에 있습니다.
- 에이전트 Command와 사용자 되돌리기는 일반 queue에서 적용되고, 에이전트 Command는 사용자 입력보다 낮은 priority로 큰 작업을 나눠 처리합니다.
- 출력 디코드와 원문 버퍼링은 UI·문서 스레드 밖에서 하며, 스트리밍 중 캔버스 지연은 성능 게이트로 검사합니다.

## Security

- 네트워크 포트가 없습니다. IPC 양쪽은 데이터 교환 전에 상대를 인증합니다(§5).
- 권한은 세션 한정입니다. §3 변경 불가 경로에 열거한 상태(프로젝트 신뢰 상태, MCP 권한 상태, 에이전트 모드, 에이전트 변경 출처 표시와 되돌리기)는 앱이 소유하고 프로젝트 파일과 Git 밖에 두므로(Consequences), 프로젝트 파일 편집이나 에이전트 경로로 바꿀 수 없고 사용자 UI에서만 바뀝니다.
- headless backend는 읽기 전용이고, 신뢰된 고정 프로젝트 하나만 다룹니다.
- 내장 세션에는 Terminal과 FileDelete가 없습니다.
- 모든 판단은 fail closed입니다.
- 인증·자격 증명·모델 호출·사용량은 CLI와 공급자 사이의 일이며 Stellar는 관여하지 않습니다(§4.1).
- 에이전트 입출력은 진단, 텔레메트리, 복구 snapshot에 넣지 않습니다(XVI.8).
- 에이전트는 자신의 출처 표시를 지우거나 되돌리기를 실행할 수 없습니다.
- 출력 디코드 결과는 문서 변경 경로와 승인 응답에 도달하지 않습니다.
- 명령줄 설치는 사용자 동의로만 합니다(2026-11-14 결정 7). 설치 위치와 안전 조건은 §37에 따라 XXIV.5에서 정합니다.
